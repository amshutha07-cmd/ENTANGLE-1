# Prior Art Search Report: Hardware-Instantiated Erasure Coding Apparatus (Dual Hardware-Rooted Reed-Solomon Parameter Split)

## TL;DR
- **The core inventive combination appears novel.** No prior art was found disclosing the central concept of Claim 1 — splitting Reed-Solomon code parameters across two physically independent hardware roots so that one source determines the finite field/primitive polynomial and the other determines the evaluation coordinates, with neither sufficient alone. The narrow combinations of Claims 1–2 (NFC silicon attestation + Reed-Solomon parameter instantiation) and the "non-zero residual polynomial as hardware-mismatch detector" are also not disclosed in the literature searched.
- **Every individual building block is well-known prior art, however.** PUF-based error correction (fuzzy extractors using Reed-Solomon/BCH), NFC/NTAG ECDSA originality signatures over a factory UID, OTP write-lock provisioning, domain-separated KDFs (HKDF/NIST SP 800-108), UID-bound key derivation, secret evaluation points in GRS-based McEliece variants, and freshness-bound co-presence/tap-to-pair protocols each exist in mature, citable form. These will be the primary obstacles for the dependent claims and for arguing non-obviousness.
- **The strongest patentability position is the specific, non-obvious combination and the unusual use of the RS residual as an attestation signal;** the weakest dependent claims are 2, 3, 6, and 7, which recite conventional techniques (NFC originality signature, OTP lock bits, hardware-derived code rate, domain-separated derivations) that a patent examiner will readily find in the references below.

## Key Findings

**1. The two-source parameter split (Claim 1 core) is not disclosed anywhere located.** A dedicated deep search across Google Patents, USPTO full-text, IEEE, IACR ePrint, ACM, and Springer found no patent or paper where one physically independent hardware secret selects the finite field/primitive polynomial and a second independent hardware secret selects the evaluation coordinates/Vandermonde geometry of the same code. The coding-theory literature universally treats field choice and evaluation-point choice as design parameters of a single code held by a single party. This is a confirmed absence and the anchor of any novelty argument.

**2. The NFC-originality-signature-plus-Reed-Solomon combination (Claims 1–2) is not disclosed.** The two technology families are mature but appear only separately. NFC chip attestation (NXP NTAG/MIFARE/ICODE, ST TruST25) and Reed-Solomon coding on RFID/NFC tags each exist, but no located reference combines chip attestation with erasure-coding-based reconstruction or tamper detection.

**3. Using a non-zero RS residual polynomial R(x) as a deliberate hardware-mismatch/tamper detector (Claim 1) is not disclosed as claimed.** All located references use the syndrome/remainder for its conventional purpose (error detection, correction, or miscorrection avoidance). The closest is a Hewlett-Packard patent that uses a deliberately chosen remainder as a data-integrity cross-check — but for miscorrection detection, not hardware attestation.

**4. Every dependent-claim technique is individually anticipated by strong prior art** (detailed below), meaning the dependent claims will likely stand or fall on their dependency from the (novel) independent claim rather than on independent inventive merit.

## Details by Claim Element

### Element 1 — Split-authority / two independent hardware roots of trust (Claim 1)
The concept of rooting trust in *two* critical hardware secrets is established but not in a coding context:
- **"Hardware-Rooted Trust for Secure Key Management and Transient Trust"** (Dwoskin & Lee, Princeton PALMS; ACM CCS 2007, DOI 10.1145/1315245.1315294). Roots trust in two secrets — a Device Root Key and a Storage Root Hash. Relevant to the general "two hardware secrets" framing but does not touch code parameters. *Reads on the generic dual-root idea; not on the RS split.*
- **US 9,094,205 "Secure provisioning in an untrusted environment."** Splits secrets into multiple pieces (e.g., three), burned into lockable fuses, combining device-fabricator and OEM trust anchors. *Relevant to Claims 1 and 3 (split secret + fuse lock) but shares are mathematical, not code parameters.*
- **US 11,743,293 and US 12,255,920 "Remote attestation transport layer security and split trust encryption."** Split-trust encryption where no single entity can unilaterally decrypt; splits a data encryption key into portions. *Reads on split-authority generally; not on RS parameterization.*
- **Threshold/Shamir secret sharing prior art** (WO2007049267A1 network security system; US 9,331,984 B2; US 11,063,754 B2 Huawei hybrid secret sharing; SPYRUS US 9,742,561). These split a *secret payload* into shares — fundamentally different from splitting a code's *algebraic parameters* across two hardware roots. *Distinguishable: shares vs. parameter-split.*

**Assessment:** The dual-hardware-root framing is known, but its application to separably determine RS field structure vs. evaluation geometry is novel. Claim 1's "neither alone is sufficient" language maps conceptually to threshold schemes, so an examiner may raise obviousness combining threshold cryptography + configurable RS codecs; the counterargument is that the split is over *code structure*, not secret shares, and produces a decode-failure attestation rather than a reconstructed secret.

### Element 2 — Code parameters derived from PUF/hardware-rooted secret (Claim 1, Claim 4, Claim 6)
This is the richest prior-art area, but the relationship is *inverted* relative to the claims:
- **US 10,819,528 and US 11,018,881 "Device security with physically unclonable functions."** Fuzzy extractor performs key generation and ECC encoding, creating a public syndrome mask as helper data. *RS/ECC corrects PUF noise; the PUF does not parameterize the code.*
- **CN 110869997 A "Secure key generation by biased physical unclonable functions"** (references WO2016/102164). Concatenated inner repetition + outer Reed-Solomon code for PUF key stabilization. *RS as helper-data layer, not hardware-parameterized code.*
- **"On Error Correction for Physical Unclonable Functions"** (Puchinger, Müelich, Bossert, Hiller, Sigl; arXiv:1501.06698) and **"Error Correction for PUFs Using Generalized Concatenated Codes"** (arXiv:1407.8034) — foundational academic work; the RS-in-PUF construction (Reed-Muller + Reed-Solomon GCC) is described as "the first that shows the potential of RS codes in the PUF context" (Springer, J. Cryptographic Engineering, DOI 10.1007/s13389-020-00223-w).
- **"A New Error Correction Scheme for PUFs"** (arXiv:1611.01960; IEEE VDE 7938055). Constructs an *individual code per PUF instance* containing the PUF response as a codeword, with no helper data. *This is the closest academic analog to "hardware-derived code construction," but the code is built to contain the response, not split across two roots, and uses LDPC not split-parameter RS.*
- **US 11,258,597 "Key derivation from PUFs"** and **EP1017177A1 / US 6,467,063 "Configurable Reed-Solomon encoder/decoder"** — the latter confirms Galois field order, primitive polynomial, and codeword parameters are settable via writable registers. *Establishes that primitive-polynomial/field selection is a known configurability feature — a likely obviousness reference against Claims 4 and 6 — but as software configuration, not a hardware secret and not split from evaluation-point selection.*

**Assessment:** Prior art abundantly shows PUF + RS/ECC, but always with the code *protecting/stabilizing* the hardware key. The claims invert this: the hardware sources *define* the code and decode-failure *is* the signal. This inversion is the novelty fulcrum. Claim 4 (UID-bound polynomial selection) and Claim 6 (hardware-derived code rate) are individually weak because UID-bound derivation (Element 6) and configurable RS parameters are both known.

### Element 3 — Decode failure / non-zero syndrome / residual as tamper/attestation (Claim 1)
- Conventional RS decoding treats a non-zero syndrome as an error indicator (e.g., US 5,719,884 "A non-zero syndrome detects that the n-symbol code block is corrupt"; US 4,413,339; textbook sources CMU, ScienceDirect). *These are the textbook baseline the claim must distinguish from.*
- **US 6,898,754 (Hewlett-Packard) "Error detection for data storage and transmission"** — deliberately chooses a remainder polynomial with roots different from the RS generator, as a cross-check to detect miscorrections. *Closest in spirit — a residual used as an integrity check beyond the base code — but it is a data-integrity/miscorrection cross-check, not a hardware-mismatch/tamper detector, and there is no hardware-secret split.*
- PUF authentication via decode/threshold failure exists (US 10,644,892; US 10,469,273 "Authentication based on a challenge and response using a PUF"; arXiv:2206.11840 sets a response threshold below 100%−BER), but failure there is a *noise/matching* threshold, not a structural code mismatch from wrong parameters.

**Assessment:** Using R(x)≠0 specifically as a *hardware-mismatch attestation* (wrong field or wrong coordinates → structurally uncorrectable → reject) is not disclosed. This is a genuinely distinctive element and a strong candidate for a narrow, defensible claim.

### Element 4 — NFC IC originality signature (Claim 2)
This is conventional, well-documented industry practice — Claim 2 is essentially anticipated as to its recited technique:
- **NXP NTAG/MIFARE/ICODE originality signatures**: die-individual ECDSA signature over the factory-burned UID, stored in ROM at production, verifiable offline against NXP's published ECC public key. Per the NXP NTAG213/215/216 datasheet (Rev. 3.2, 2 June 2015): "Each NTAG21x UID is signed with a NXP private key and the resulting 32-byte signature is stored in a hidden part of the NTAG21x memory during IC production… NTAG21x digital signature is based on standard Elliptic Curve Cryptography (curve name secp128r1), according to the ECDSA algorithm," retrieved via the READ_SIG command and verifiable offline. Curves vary by product: secp128r1 (NTAG213/215/216, Mifare Ultralight EV1), secp224r1 (NTAG424 DNA). NXP Application Note AN11350 ("NTAG Originality Signature Validation") specifies verification of the die-individual ECDSA signature over the factory UID using curve secp128r1 with NONE hashing and IEEE P1363 encoding (16-byte R, 16-byte S), verifiable in software (e.g., OpenSSL/Easy-Ecc) against NXP's published ECC public key; AN12196 covers the NTAG 424 DNA equivalent. ST TruST25 offers an equivalent ECC scheme.
- **US 10,397,000 "Multi-level authentication for secure supply chain asset management"** — NFC UID + ECDSA signature + Speck; challenge/response + UID + ECDSA verified before decryption. *Reads squarely on the NFC-attestation portion of Claim 2.*

**Assessment:** Claim 2's recited NFC originality-signature verification is standard prior art (NXP AN11350/AN12196). Claim 2 is patentable only through its dependency on the novel Claim 1; its recited NFC technique adds nothing independently inventive.

### Element 5 — OTP write-lock immutability (Claim 3)
Conventional and heavily patented:
- **US 10,205,588 and US 11,018,847 "Device keys protection"** — secure element with OTP memory containing locked/unlocked bits, irreversibly pre-programmed lock bits; device-specific value programmed then global value erased. *Directly on point for Claim 3's OTP lock mechanism.*
- **US 8,032,727 "Method and system for locking OTP memory bits after programming"** — general OTP lock-after-write. Silicon Labs AN1218/AN1271 (immutable OTP storing public sign key, locked for device life) and Analog Devices AN2604 (locked pre-provisioned secure elements) corroborate industry practice.

**Assessment:** Claim 3 recites conventional OTP provisioning. Patentable only via dependency; no independent inventive weight.

### Element 6 — UID-bound deterministic parameter derivation (Claim 4)
- The STM32 96-bit unique device ID is used with cryptographic primitives to derive security keys. Per ST reference manuals (e.g., RM0451 §25.2), the 96-bit UID comprises "UID[31:0]: X & Y coordinates on the wafer (BCD); UID[39:32]: WAF_NUM wafer number; UID[63:40] & UID[95:64]: LOT_NUM (ASCII)"; ST states it is "guaranteed to be unique for all STM32" and useful "for applications that need a key that can be used for security applications." IEEE 802.1AR IDevID/LDevID binds identifiers to a device UID. US 10,042,989 "Device activation" combines per-service seed segments with a UID and distinct cryptographic primitives.
- Key-dependent/UID-dependent selection of algebraic structures (S-boxes, polynomials) is known: arXiv:1711.09166 (S-box generation from polynomials over Galois fields).

**Assessment:** UID-bound derivation such that identical secrets on different devices produce different outputs is a known technique. Claim 4 is weak standing alone; its novelty is only in binding this to primitive-polynomial selection within the Claim 1 split.

### Element 7 — Freshness-bound co-presence / tap-to-pair (Claim 5)
- **US 10,924,925 "Secure pairing for devices with NFC tags equipped with authentication"** — challenge/response where a challenge seed is combined with a shared secret and private key; ties to Bluetooth SSP numeric-comparison pairing. *Reads on the freshness-bound challenge-response and co-presence portion of Claim 5.*
- Analog Devices app note "No connection, No problem" describes NFC challenge-response with a random nonce to defeat replay. FIDO2/WebAuthn attestation embeds a fresh one-time server challenge; the W3C Web Authentication specification (§Cryptographic Challenges) states: "In order to prevent replay attacks, the challenges MUST contain enough entropy to make guessing them infeasible. Challenges SHOULD therefore be at least 16 bytes long." arXiv:1808.03320 surveys context-based co-presence detection.

**Assessment:** Freshness-bound, replay-resistant co-presence and challenge-binding-to-UID are established. Claim 5's novelty rests only on binding C₂ derivation to the simultaneous presence of both RS-parameter sources — inventive only in the Claim 1 context.

### Element 8 — Domain-separated KDFs (Claim 6, Claim 7)
Purely conventional cryptographic engineering:
- **NIST SP 800-108** (KDF using PRFs with Label ‖ 0x00 ‖ Context ‖ [L]₂), **RFC 5869 (HKDF)** with the `info` field for context/label domain separation, and libsodium's `crypto_kdf` context strings all define exactly this. IACR ePrint 2025/657 ("Key Derivation Functions Without a Grain of Salt") formalizes multi-input/n-KDFs with per-source context and per-output labels. Wikipedia "Domain separation" documents the primitive.

**Assessment:** Claims 6 and 7 recite textbook domain-separated derivation. No independent inventive weight; patentable only via dependency.

### Element 9 — General PUF + erasure/RS coding landscape
Mature field, all with RS *stabilizing* the key rather than being *parameterized by* hardware: fuzzy extractors/secure sketches (Dodis et al. lineage), code-offset constructions with BCH+repetition and RS+Reed-Muller GCC (arXiv:1501.06698, 1407.8034, Springer DOI 10.1007/s13389-020-00223-w), fuzzy vault PUF key storage (PMC10098537), reverse fuzzy extractors for RFID (Van Herrewege et al.), and anti-counterfeiting PUF tags (US 11,075,769 B2 self-forming 3D PUF pattern). US 9,703,989 and US 10,657,247 cover secure PUF error-correction circuits.

### Element 10 — Secret evaluation points in RS/GRS codes
Secret evaluation points appear only in code-based public-key cryptography (the context the invention operates *outside* of):
- GRS-based McEliece/Niederreiter variants where the secret support (evaluation points α) and column multipliers form the private key (arXiv:1204.6459/1307.6458 distinguisher attacks; Springer DOI 10.1007/s10623-014-9967-z; Bogdanov–Lee homomorphic encryption arXiv:1111.4301, where "the (randomized) evaluation points of the Reed-Solomon code are not revealed in the public key"). Twisted RS codes (arXiv:1801.07003) choose evaluation points "in a suitable way" to resist structural attacks.

**Assessment:** Secret/hidden RS evaluation points are known in code-based cryptography — an examiner may cite these against the "evaluation coordinates as secret" aspect. But these are software private keys in a PKC encryption/decryption context, never *hardware-derived* and never *split* from the field-structure secret, and they are not used to produce a decode-failure attestation. This distinction supports novelty.

## Recommendations

**Stage 1 — Anchor the claims on the confirmed-novel combination (do now).** Draft the strongest independent claim tightly around the two elements with no located prior art: (a) the *separable* derivation of field structure from one hardware root and evaluation geometry from a second independent root, neither sufficient alone; and (b) the non-zero RS residual as a *hardware-mismatch attestation* output. Emphasize the "inversion" versus PUF+RS art (hardware defines the code; decode-failure is the signal) explicitly in the specification to preempt the strongest obviousness combination (configurable RS codec + threshold cryptography + PUF fuzzy extractor).

**Stage 2 — Reposition or fold the weak dependent claims.** Claims 2, 3, 6, and 7 recite conventional techniques (NFC originality signature per NXP AN11350/AN12196; OTP lock bits per US 10,205,588; hardware-derived code rate; domain-separated KDF per NIST SP 800-108/RFC 5869). Keep them only as dependents (their dependency on a novel independent claim preserves validity) but do not rely on them for independent inventive merit. Consider adding dependent claims capturing *how* the residual magnitude distinguishes a field mismatch from a coordinate mismatch — a space with no located art.

**Stage 3 — Commission an examiner-grade classification search before filing.** This was a web-level search of abstracts, snippets, and full-text where accessible. Commission a professional CPC-class search — H03M13/15 (Reed-Solomon), H04L9/0866 and H04L9/3278 (key generation from physical characteristics/PUF), G06F21/70–79 (hardware security), and G09C1/00 — plus non-English (CN/JP/KR) databases and assignee-focused sweeps of NXP, Intel, Synopsys/Intrinsic-ID, and Block/Square portfolios. **Threshold that changes strategy:** if that search surfaces any reference splitting code parameters across two roots, or using a residual as an attestation signal, narrow to the residual-magnitude discrimination claims; if it confirms absence, pursue broad independent claims.

**Stage 4 — File provisionally now to secure priority,** given the confirmed absence of direct hits, then use the 12-month window for the Stage 3 formal search and continuation strategy.

## Caveats
- **Absence of evidence caveat.** "Not found" reflects a web-level search (Google Patents/USPTO snippets and abstracts, plus accessible full text). It is not equivalent to an examiner-grade classification search and does not cover most non-English patent literature, NDA-restricted vendor documentation, or unpublished/recently filed applications within the 18-month publication blackout. Confirmed-absence findings are strong signals, not guarantees.
- **Obviousness risk is real even without anticipation.** Each building block is individually well-established. A skilled examiner may argue the combination is obvious by aggregating configurable-RS-codec art (EP1017177A1), PUF+RS fuzzy extractors, NFC originality signatures, and threshold cryptography. The defense is the specific, counter-intuitive inversion (decode-failure as attestation) and the field/coordinate separation across roots — these should be argued as producing an unexpected result (attestation without stored keys, key transmission, or key derivation from the codeword).
- **Secret-evaluation-point art in code-based cryptography (McEliece/GRS variants) is the most likely §103 reference** for the "evaluation coordinates as secret" limitation and should be addressed head-on in the specification.
- No single located reference reads on all of Claim 1; the risk is combinatorial (obviousness), not anticipatory (novelty).
